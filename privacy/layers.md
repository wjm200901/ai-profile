# 隐私分层

> 核心判断：**你能不能安全地公开这份档案？** 答案取决于你是否做了物理隔离。
> 靠"我会注意的"必然翻车；靠仓库结构和自动扫描才可持续。

## 三档定义

| 级别 | 谁能看 | 放哪里 | 例子 |
|---|---|---|---|
| **public** | 所有人、所有模型 | 本仓库 `main` 分支 | 职业方向、方法论、公开项目结果 |
| **semi-public** | 可公开，但需要语境 | 本仓库，但标注 `visibility: semi-public` | 合作方行业（不写名字）、失败经历（不牵连他人） |
| **private** | 只有你 | **永不进入本仓库**：本地 `private/`（已 gitignore）或独立私有仓库 | 联系方式、收入、客户名单、家庭信息、未公开项目 |

## 实现方式（按可靠性排序）

1. **物理隔离（最可靠）**：private 内容放另一个私有仓库，公开仓库只在 `privacy/layers.md` 里写"存在，但不在这里"。
2. **分支隔离**：`main` 公开、`private` 分支不推送到公开远端（注意：GitHub 上分支是可见的，除非用独立仓库）。
3. **本地目录 + gitignore**：`private/` 目录已写入 `.gitignore`，只在本机存在。
4. **自动扫描（兜底）**：`scripts/validate.py` 会在提交前扫描敏感模式。

## 敏感模式清单（脚本会自动检查）

| 类型 | 正则意图 | 处理 |
|---|---|---|
| 手机号 | 1 开头的 11 位数字 | 拦截 |
| 身份证 | 17 位数字 + 校验位 | 拦截 |
| API Key | `sk-`、`ghp_` 等前缀 | 拦截 |
| 私钥 | `BEGIN ... PRIVATE KEY` | 拦截 |
| 邮箱（非公开） | 非 `example.com` 的私人邮箱 | 警告 |

> 扫描只能兜底，不能替代判断。**真正的防线是：写之前先问"这句话被未来的雇主/客户/家人看到，我会不会不舒服"。**

## 发布前人工检查清单

- [ ] 全文搜索真实个人信息（学校名、城市、同学姓名、照片路径），确认没漏
- [ ] 没有精确住址、公司内部代号、未公开营收
- [ ] 提到的人：公众人物可直接写；非公众人物已获同意
- [ ] 失败经历里没有可识别的第三方
- [ ] `identity/06-boundaries.md` 的授权级别写清楚了
- [ ] 想清楚仓库是 public 还是 private：**建议 public 骨架 + private 细节**

## 如果只想公开一部分

两个可行方案：

1. **双仓库**：`ai-profile`（public，骨架与方法论）+ `ai-profile-private`（private，细节）。公开仓库在 `README.md` 里说明"细节在私有仓库，可按需申请"。
2. **单仓库 + 脱敏**：所有内容都公开，但把具体数字换成量级（"1.2 万家庭"→"万级家庭"），把公司名换成行业。

## 一个反直觉的建议

**不要试图隐藏"你在隐藏什么"。** 在 `identity/06-boundaries.md` 里明确写出"有些内容不在公开档案里"，比假装透明更可信，也更能防止模型自行脑补。
